# ADR-0004: SQLite (WAL) only for v1 — no Postgres, and no abstraction pretending otherwise

**Status:** accepted (Phase 0), built.

## Decision

One database engine: **SQLite in WAL mode**, via `modernc.org/sqlite`. No
Postgres support in v1, and **no repository abstraction written to keep the
option open**.

Jacob's brief allowed either behind a repository layer. The layer is the part
being declined.

## Why SQLite

At ≤25 users and ≤100k library items, with ~5 concurrent streams, SQLite is not
a compromise — it is the correct engine. It removes a service to run, a
credential to manage, a backup to get right separately, and a failure mode where
the application is up and the database is not.

It also keeps [ADR-0002](0002-go-no-cgo.md) intact. `modernc.org/sqlite` is a
pure-Go translation rather than a binding, so the binary stays static and no C
parser enters the process. It is slower than the cgo driver, which does not
matter at this scale and is the price of that property.

## Why no portability layer

A repository interface written to support an engine nobody runs does not
actually support it. It supports the *subset* somebody imagined while writing
it, and the moment real work needs a partial index, `ON CONFLICT DO UPDATE`, or
SQLite's particular locking behaviour, the abstraction either leaks or blocks
the work.

What it reliably does is make every query worse, forever, in exchange for a
migration that may never happen and would need re-testing end to end regardless.

So the schema uses SQLite deliberately — including where the two engines differ
— and if Postgres is ever needed, the work is a real port, done once, with the
tests as the specification. That is more honest than a layer whose purpose is to
make the port look cheap.

The containment is different and stronger: **only `internal/platform/db` and the
per-domain repositories may build SQL.** Nothing above them writes a query, so a
port has a defined blast radius even without a portability interface.

## The pragmas are not tuning

Stated in the package header, and worth repeating because each one is a
correctness property:

- **`foreign_keys=ON`** — SQLite defaults this **off**, which silently turns
  every declared `REFERENCES` into a comment. The references in
  [DATA-MODEL.md](../DATA-MODEL.md) are enforced because of this line.
- **`journal_mode=WAL`** — required for readers concurrent with a writer.
- **`busy_timeout`** — stops the single-writer model surfacing as `SQLITE_BUSY`
  under normal contention.
- **`synchronous=NORMAL`** — the correct pairing with WAL: durable across a
  process crash, at risk only from an OS-level crash.

## Migrations

Numbered, embedded in the binary, applied at startup, and **checksummed** — a
migration edited after being applied is detected rather than silently
desynchronising deployments.

[DATA-MODEL.md](../DATA-MODEL.md) is generated by applying them to a throwaway
database and reading the result back, so the document cannot describe a schema
the migrations do not produce.

## Consequences

- **One writer.** Long transactions are a correctness concern, not a performance
  one. Nothing holds a write transaction across an HTTP request.
- **Backups are a file copy** of a consistent snapshot, not `pg_dump` — simpler,
  and one fewer thing to get wrong at 3 a.m.
- **Postgres is a port, not a config switch.** Written down here so nobody
  discovers it by grepping for a connection string.
